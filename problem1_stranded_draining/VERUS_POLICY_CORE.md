# Verus Policy Core Plan

This milestone treats `src/policy_core.rs` as the boundary between executable
scheduler code and future verification.

## Scope

We do not try to verify arbitrary sched-ext source code. The supported shape is:

```text
fixed rustland-style adapter
  -> runtime wrapper
    -> Verus-friendly policy core
```

The fixed adapter receives a reusable environment specification. Each scheduler
under verification must express its policy as a pure state machine that consumes
explicit inputs and emits explicit actions.

## Current Conversion Strategy

For the first milestone, `policy_core.rs` is written directly in a restricted
Rust subset rather than generated by a converter. A Verus-facing entry point can
reuse the same structures:

```text
PolicyInput
PolicyCore
PolicySnapshot
PolicyAction
```

The real runtime interprets actions as side effects:

```text
Dispatch(TargetCpu)    -> bpf.dispatch_task(target_cpu)
Dispatch(RecoveryCpu)  -> bpf.dispatch_task(recovery_cpu)
Dispatch(Any)          -> bpf.dispatch_task(RL_CPU_ANY)
HoldGate               -> bounded thread::sleep in deterministic mode
Emit(event)            -> JSONL adapter trace
```

The Verus model interprets the same actions abstractly:

```text
Dispatch(...)  -> an emitted scheduler decision
HoldGate       -> an environment scheduling point
Emit(event)    -> ghost trace event or ignored observation
```

## Allowed Core Shape

The policy core may use:

- explicit structs and enums for state, inputs, events, and actions;
- deterministic state transitions;
- integer identifiers for tasks, CPUs, LLCs, and enqueue generations;
- simple collections representing scheduler queues.

The policy core must not use:

- BPF or sched-ext calls;
- wall-clock time, `Instant`, or `Duration`;
- `thread::sleep`;
- sysfs or procfs reads;
- JSON printing or logging side effects;
- hidden environment effects inside helper methods.

Runtime-only behavior must be represented as a `PolicyAction` or a
`PolicyInput`. For example, recovery timing is represented as
`PolicyInput::RecoveryDeadlineElapsed`; only the runtime wrapper decides when
real time has elapsed.

## Problem 1 Property Boundary

For Problem 1, the key observable snapshot is:

```text
q > 0 && c == false && d == false
```

`PolicyCore` reaches that snapshot only after the bad interleaving:

```text
EnqueueSelect
PublishMask
UpdateObserveQueue
EnqueueCommit
DispatchTick -> StableInvalidState
```

The real adapter test must still prove that this abstract sequence is reached
through the actual sched-ext enqueue path.

## Future Converter

A later converter can accept a larger Rust policy subset and produce a
Verus-friendly core automatically. That is a separate research step. The first
trust boundary is intentionally simpler: scheduler authors write directly
against the policy-core interface, and the same core is both executed and
verified.
